# ADR-0001：独立重建与选择性复用

状态：Accepted
日期：2026-08-14

## 背景

旧 ParaEGOX 在长期 Agent 驱动开发中积累了大量候选实现、控制面、协议、文档和验证分支，但最基本的 TUI 与有上下文 Agent 对话没有成为 main 上持续成立的产品闭环。继续在原仓库叠加修改，会同时继承不清晰的实现状态、过早抽象和难以审查的历史。

用户已经决定创建全新的 Paraegox 仓库，不 fork PhanthyMotus，也不继承旧 ParaEGOX 的 Git 历史。旧 ParaEGOX、EAGOS 和 PhanthyMotus 仍包含有价值的产品原则、代码经验和失败样本。

## 决定

- Paraegox 是新的独立实现，拥有新的 Git 历史和 main 权威。
- Paraegox 不 fork PhanthyMotus，不把旧 ParaEGOX 工作树或候选分支作为代码基线。
- 旧仓库的文档、ADR 和实现状态都是历史输入，不自动成为本仓库的 Accepted 决定或已实现能力。
- 复用从可观察行为、失败语义和测试场景开始，再实现满足当前切片的最小代码。
- 禁止目录级复制旧实现，也不为映射旧架构图而预建 crate、服务、协议和占位模块。
- 只有当前路径确实需要时才复制源代码；复制时必须检查并保留适用许可证、版权和归属。

Clean slate 不等于忽略历史。旧系统中已经验证的边界和失败经验应通过 Research 被重新表述，再按本仓库的用户目标和当前消费者进入 Architecture、ADR 或实现。

## 考虑过的替代方案

### 继续旧 ParaEGOX 仓库

拒绝。它保留历史连续性，但也保留未合入候选、权威漂移和过早控制面，难以为每次新变更建立清晰基线。

### Fork PhanthyMotus

拒绝。它提供现成 Git 血缘，但会把新系统的产品边界与原项目结构绑定，不能表达本次独立重建。

### 批量复制旧代码后逐步删除

拒绝。删除式重构很容易保留隐式依赖、旧协议和无消费者抽象，并让最小产品路径继续被基础设施阻塞。

## 后果

正面后果：

- main 从第一天起保持可解释、可构建和可验证。
- 每个新抽象必须证明当前 producer、consumer 与失败场景。
- 可以继承经验而不继承旧实现规模和治理负担。

负面后果：

- 某些已经存在的能力需要重新实现。
- Git 不会自动提供旧实现的逐行历史。
- 任何源代码复用都需要单独完成许可证与归属检查。

## 范围与重审条件

本 ADR 决定仓库血缘和复用方式，不决定具体 transport、TUI、模型供应商、crate 划分或部署技术。

只有用户明确改变仓库血缘或代码复用政策时才重审本 ADR。后续实现进度不得追加到本文件。
